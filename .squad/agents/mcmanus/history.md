### 2026-07-06 — Polish pass: the three Hockney findings (all in `blog.css` + `footer-scripts.html`)

Cleared the three non-blocking findings. Two files, all additive/subtractive — no restyle. Staged, not committed.

1. **Focus ring (a11y §5).** `.search-trigger` (hero ⌘K) and `.cmd-palette-hint` (nav ⌘K badge) are both `<button>`s that fell back to the UA outline. Added one combined rule next to `.search-trigger:hover` in §14: `.search-trigger:focus-visible, .cmd-palette-hint:focus-visible { outline: 2px solid var(--focus-ring); outline-offset: 2px; }` — same convention as `.nav-links a:focus-visible`. Verified with **real keyboard focus** (Tab), not programmatic `.focus()`: `el.matches(':focus-visible')` = true and computed outline `rgb(249,115,22)` on both. **Gotcha:** programmatic `.focus()` does NOT engage `:focus-visible` in Chromium — you must tab to the element. Second gotcha: the hint is a *desktop-nav* pill (hidden in mobile layout), so test it at ≥ desktop width; the trigger is on the homepage hero. Third: the integrated browser runs at ~80% page zoom, so `getComputedStyle` reports `2px` as `1.6px` (width AND offset scale identically) — check the ratio/color, not the raw px.

2. **Prose-link overflow + row spill.** Added `.blog-post a { overflow-wrap: anywhere; }` (matches the existing `.post-heading h1` treatment). **Proved it's load-bearing:** A/B toggling the rule off at 320px pushes a `.blog-post a` past the content box on **23 posts** (link right-edge jumps ~220→450px); with the rule every link stays in bounds, 0 offenders. Also resolved Hockney's un-carded row spill by neutralizing Bootstrap's negative gutters that `padding-inline:0` stopped absorbing — one combined rule for both structural containers: `.header-section .container-md > .row, .container-md.post-body > .row { margin-inline: 0; }`. Confirmed computed row margins now `0px/0px` and nav/footer/TOC all sit at the viewport edge. No card chrome reintroduced; offsets are on the child cols so they're untouched.

3. **Dead JS.** `_includes/footer-scripts.html` was a single `DOMContentLoaded` handler doing two now-inert things: a `[data-delay]` loop (home moved to inline `--delay` + CSS `animation-delay`) and a `.read-more-chip` click-shim (chip removed in M2). Both querySelectors returned empty → verified null-safe/dead. Replaced the whole `<script>` with a Liquid comment placeholder (the `{% include %}` in `base.html:42` stays valid). Re-verified the homepage entrance still animates via CSS (`animationName: rise`, staggered delays, opacity 1) with **zero console errors**.

**Verification method (kept honest):** full 54-post crawl at 320px over HTTP (`_site_check`, deleted after). Along the way I characterized the *remaining* 320px horizontal scroll, which the finding under-specified: the dominant driver is the **off-canvas `.mobile-drawer`** (`position:fixed`, translated to right≈423 → ~35px real scroll on ~48 posts, `canScrollRight` confirms it; homepage is clean). A couple of posts also overflow on **non-link prose** the link-scoped rule can't reach — long unbroken `<em>` placeholder tokens (`ProjectName`, `ExampleAccountName`) and one **unconstrained `<img>`**. All three are **pre-existing and untouched by this pass** (I only touched `.blog-post a`, the two `> .row`s, the two `:focus-visible`s, and the dead script) and are **out of scope** for the three-fix mandate — flagged for the team in `decisions/inbox/mcmanus-polish-pass.md`, not fixed here. Lesson: "no h-scroll at 320px" is a page-level claim; a link-scoped `overflow-wrap` only clears the *link* portion — verify per-cause (drawer vs prose token vs image vs link), and don't let a red-herring "widest descendant" inside an `overflow:auto` code block masquerade as the document-overflow culprit (walk up for a clipping ancestor first).
