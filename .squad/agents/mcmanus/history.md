### 2026-07-07 — Homepage grid-completeness: featured-lead needs an index count divisible by every column regime

Marcus spotted an empty card slot in the last row of the homepage grid. Root cause: `_layouts/home.html` looped `{% for post in site.posts limit: 12 %}`, and `forloop.first` renders as the full-width `.post-card--featured` lead (`grid-column: 1 / -1`, its own row), leaving **11** index cards. 11 divides evenly into no multi-column regime → gap in the last row at 3-col (3·3·3·2) and 2-col (2·5+1). **Fix: `limit: 12` → `limit: 13`** (1 featured + **12** index). One-line change plus a `{% comment %}` explaining the math so nobody "tidies" it back to 12.

**Row-math rule (durable).** With a full-width featured lead + N index cards flowing in a grid, **N must be a multiple of the LCM of every active column count** or the last row has holes. The homepage grid is `.post-cards-container.modern-grid` = 3 (>1024px) → 2 (641–1024) → 1 (≤640); LCM(3,2)=6. **12 is divisible by 6 — and by 4** — so it fills complete rows at 3-col (4 rows), 2-col (6 rows), *and* the legacy 4-col regime that still governs >1200px (see below). 12 is the robust choice; 11 was the worst possible (divisible by nothing). Rule of thumb: index cards ∈ {6, 12, 18, …}.

**Two grid systems coexist in `blog.css` — know which governs.** Legacy §5/§11 `.post-cards-container` (`repeat(4,1fr)` base; 3/2/2/1 at max-width 1200/992/768/576) is still in the file; the editorial `.post-cards-container.modern-grid` (§ near line 3046: `repeat(3,1fr) !important`; 2 @1024, 1 @640) wins on the homepage by two-class specificity + `!important`. **Caveat I verified:** above **1200px** none of the legacy max-width queries apply, so the winner there is editorial-base-3col-`!important` vs legacy-base-4col-normal → editorial 3-col wins (confirmed 3 tracks at cssWidth 1280). The featured `grid-column: 1 / -1` was verified to span the **full container width** at both breakpoints (`featured.width ≈ grid.width`).

**Verification gotchas (cost me several wrong readings — all now confirmed):**
1. **The integrated browser CACHES `blog.css`.** The live `:4000` tab rendered the *pre-redesign 4-col legacy* grid even though `curl http://localhost:4000/assets/css/blog.css` returned the **current** file (byte-identical to source, 85672 B, contains `.post-cards-container.modern-grid`). A stale cached stylesheet masquerades as a cascade bug. **Always** (a) curl the served asset and diff bytes vs source, and (b) verify render on a **fresh port + `forceNew` page** (I built to `_site_check`, served on `:4011`, measured there). Don't trust the long-lived preview tab for CSS-cascade claims.
2. **Scale factor is ~2/3, not ~0.8.** `setViewportSize({width})` maps to `window.innerWidth = width × 0.667` here (req 1920 → 1280 CSS px; 1200 → 800). Request `target × 1.5` and always read back `window.innerWidth`; never assume the requested width is the CSS width the media queries see. (Refines the earlier "~80% zoom" note.)
3. **The staggered `fade-in-up` entrance animation skews row detection.** Mid-`translateY`, cards in the same grid row report different `getBoundingClientRect().top`, so top-clustering invents phantom rows (`[3,4,4,1]`). `getAnimations().finish()` right after `goto` was unreliable (elements not yet animating). **Reliable:** `page.addStyleTag({content:'.fade-in-up{animation:none!important;transform:none!important;opacity:1!important}'})` before measuring → clean equal tops per row (`[3,3,3,3]` / `[2,2,2,2,2,2]`).

**Test contract:** `tests/landing.spec.ts` does **not** assert a total grid card count — only `.post-card--featured` = 1 (still true) and `cardCount > 0`. No test change needed for the limit bump; flagged in the summary regardless so the coordinator can route to Hockney if a count guard is ever wanted.
